# 单机课表生成与智能调课 Agent 设计

## 1. 背景

现有系统使用 React、FastAPI、OR-Tools、Clerk 和 MongoDB，能够生成周课表并进行人工编辑。目标是将其重构为无需登录、启动即用的单机课表工具，并增加一个基于确定性规则与 OR-Tools 的调课 Agent。

系统只在一台电脑上运行。数据使用本地 JSON 文件保存，不考虑多人并发、账号权限、云同步、节假日或调休。基础课表只设置周一至周六；教师缺勤和繁忙使用真实日期描述，系统将日期映射到对应星期和课节。

## 2. 目标

系统应当支持：

1. 根据班级课程与每周课时、教师授课资格与带班关系、教师空闲时间、教室和走班关系生成基础周课表。
2. 处理教师的真实日期缺勤。教师缺勤期间全天不可授课，优先在原课节安排同科教师代课；无法直接代课时，通过班内局部调课，把课程移动到同科代课教师有空的课节。
3. 处理教师的真实日期繁忙。教师只在指定日期和课节不可授课，优先与受影响班级的其他教师进行班内换课，无法换课时再安排同科代课。
4. 长期缺勤采用调课方案后，形成持续生效的新周课表版本。原教师恢复后接手调整后的课节，不自动恢复旧版本。
5. 支持同步走班块。例如 1 班和 2 班在同一课节分别去 301 教室上地理、302 教室上政治；两个班、两门课程、两位教师和两间教室属于同一个不可拆分的同步块。
6. Agent 只生成一至三个候选方案。用户查看完整差异并确认后，系统才修改 JSON 数据。
7. 删除 Clerk、登录注册、用户身份和 MongoDB，打开根路径后直接进入课表管理界面。

## 3. 非目标

本次重构不包括：

- 多用户、权限、账号或网络协同。
- 节假日、调休、临时停课日和复杂校历。
- 将缺勤课程延期到教师恢复以后补课。
- 使用不具备相应科目资格的教师代课。
- 自动迁移 MongoDB 中的历史数据。
- 大语言模型调用。Agent 的决定完全由业务规则、约束求解和可解释评分产生。

## 4. 核心术语

### 4.1 基础周课表

周一至周六的重复课表模板。课表版本通过 `effectiveFrom` 指定生效日期。

### 4.2 缺勤

教师在真实起止日期内全天不可授课。星期日不产生受影响课程。

### 4.3 繁忙

教师仍然正常工作，但在一个或多个真实日期的指定课节不可授课。

### 4.4 日期例外

只影响指定真实日期的代课、换课或临时调课记录。短期变更结束后，系统自然回到当时生效的基础周课表版本。

### 4.5 长期缺勤

默认指连续 28 个自然日或以上的缺勤。阈值保存在系统设置中，可以在本地设置页修改。

### 4.6 同步走班块

由多个行政班在同一时间参加的分组课程。一个走班块包含来源班级、分组科目、每组教师和教室。课表中各来源班级引用同一个走班块；移动时必须整体移动，但教师代课可以只替换其中受影响的科目分组。

## 5. 总体架构

系统分为前端和 FastAPI 后端。后端内部划分为五个职责单一的模块：

1. **基础排课器**：使用 OR-Tools CP-SAT 生成完整周课表。
2. **调课 Agent**：根据变更事件产生候选方案，并对局部范围进行优化。
3. **统一校验器**：校验基础课表、人工编辑和 Agent 方案所遵循的共同约束。
4. **课表版本服务**：解析某个日期使用的基础版本，并叠加已确认的日期例外。
5. **JSON 数据仓库**：负责加载、验证、原子保存和备份本地数据。

前端保留创建基础数据、生成课表、查看/编辑课表和智能调课四类主流程。根路径 `/` 直接显示课表管理页；登录、注册、单点登录回调和用户菜单全部删除。

## 6. 领域数据模型

存储根对象包含：

```json
{
  "schemaVersion": 1,
  "revision": 1,
  "settings": {},
  "teachers": [],
  "classes": [],
  "subjects": [],
  "rooms": [],
  "courseRequirements": [],
  "splitCourseBlocks": [],
  "timetableVersions": [],
  "changeEvents": [],
  "appliedChanges": []
}
```

所有实体使用本地生成的 UUID，不再使用 MongoDB ObjectId 或 Clerk `userId`。

### 6.1 教师

教师记录至少包含：

- `id`、`name`。
- `qualifiedSubjectIds`：允许教授和代课的科目。
- `teachingAssignments`：班级、科目和每周课时。
- `weeklyUnavailableSlots`：固定不可用的星期和课节。

同科代课资格只能由 `qualifiedSubjectIds` 判断，不能因为教师临时有空就跨科代课。

### 6.2 班级课程要求

`courseRequirements` 记录班级、科目、每周课时、指定教师，以及是否需要连堂、实验室或指定教室。每周课时是基础排课和调课后的硬约束。

### 6.3 结构化课表单元

课表单元不再依赖 `Subject(Teacher)` 字符串解析，而是保存结构化引用：

- 普通课程：课程要求、科目、教师和教室 ID。
- 走班课程：走班块 ID。
- 空课节：`null`。

API 可以额外返回适合展示的科目、教师和教室名称，但名称不是关联主键。

### 6.4 同步走班块

走班块包含：

- `sourceClassIds`：例如 1 班和 2 班。
- `periodsPerWeek`。
- `groups`：每个分组的科目、教师和教室。

示例走班块中，地理组由张老师在 301 上课，政治组由王老师在 302 上课。1 班和 2 班课表在同一个位置引用该走班块。

### 6.5 课表版本

每个版本包含：

- `id`、`name`、`effectiveFrom`。
- `parentVersionId`。
- 周一至周六的结构化班级课表。
- 根据班级课表重建的教师与教室索引。
- 创建原因、创建时间和来源变更事件 ID。

查询某个日期时，选择 `effectiveFrom` 不晚于该日期的最新版本，再叠加该日期的已确认例外。

已生效版本是不可变的。人工编辑和长期调课都创建带 `parentVersionId` 的子版本，避免历史日期的课表被后续修改。版本中的教师分配表示事件结束后的长期安排；缺勤期间的代课教师只保存在日期例外中。

### 6.6 变更事件与已应用变更

缺勤事件保存教师、开始日期和结束日期。繁忙事件保存教师以及一个或多个 `{date, period}`。事件还保存类型、说明、创建时间和处理状态。

已应用变更保存：

- 来源事件和基础课表版本。
- 用户确认的策略与评分。
- 修改前后的结构化差异。
- 日期例外。
- 如果产生长期新版本，则保存新版本 ID。

未确认的候选方案不写入 JSON。

## 7. 基础排课规则

基础排课器继续使用 OR-Tools CP-SAT，并共享统一校验器中的规则定义。硬约束包括：

- 每个班级、每位教师和每间教室同一课节最多一个占用。
- 满足各班各科每周课时。
- 教师必须具备授课资格并遵守固定不可用课节。
- 指定教室、实验课、连堂课和每日同科上限等现有有效规则继续生效。
- 同步走班块的所有来源班级必须在同一课节引用同一个块。
- 走班块中的教师和教室不能与其他课程冲突。

生成失败时返回按约束类型分类的诊断，不保存不完整课表。

## 8. 调课 Agent 决策流程

### 8.1 通用步骤

1. 根据事件中的真实日期，找出对应生效版本和实际受影响课程。
2. 冻结与事件无关的课程，只建立受影响班级、教师、教室和走班块的局部搜索范围。
3. 按事件类型执行优先策略。
4. 直接策略不可行时，调用 CP-SAT 做局部优化。
5. 使用统一校验器复核每个候选方案。
6. 返回最多三个不同的完整可行方案及解释；不返回违反硬约束的部分方案。

### 8.2 缺勤策略

缺勤教师在整个日期范围内被视为硬性不可用。

处理顺序为：

1. 在原课节安排具备同科资格且没有冲突的教师代课。
2. 原课节无人可代时，在同一周内寻找同科教师有空的其他课节，并在受影响班级内部交换课程，使该教师能够代课。
3. 仍不可行时扩大到少量相关课程的局部调整，但不得让缺勤教师上课、不得跨科代课、不得把课程延期到恢复以后。
4. 无完整方案时返回无解原因和冲突课节。

调整后，各班每周各科课时必须保持不变。每天的分布可以改变。

### 8.3 繁忙策略

繁忙只封锁事件明确指定的真实日期和课节。

处理顺序为：

1. 优先在受影响班级内寻找双方教师都可行的直接换课。
2. 无法换课时，在原课节寻找具备同科资格的代课教师。
3. 仍不可行时进行少量相关课程的局部调整。
4. 无完整方案时返回无解原因。

“班内换课优先于代课”只适用于繁忙，不适用于全天缺勤。

### 8.4 走班策略

走班块中的某位教师缺勤时，优先只替换其对应分组的同科教师，其他分组、来源班级和课节不变。如果必须移动课节，则整个走班块一起移动，并重新校验所有来源班级、分组教师和教室。

走班块的移动成本高于普通课程，以减少对多个班级的连锁影响。

## 9. 候选方案评分

先按事件类型执行策略优先级，再在同一策略层级内使用以下目标进行字典序最小化：

1. 修改的课表单元数量。
2. 受影响班级数量。
3. 涉及教师数量。
4. 移动的走班块数量。
5. 与原星期和课节的距离。
6. 同一天同科课程分布的变化。

缺勤时，“原课节直接同科代课”优先于“为了同科代课而调课”。繁忙时，“直接班内换课”优先于“同科代课”。这些优先级不能被较小的次级数值成本反转。

每个方案向用户展示策略名称、选择原因、分项评分、完整差异、受影响对象和警告。

## 10. 日期与版本行为

### 10.1 日期解析

系统使用本机时区的 ISO 日期 `YYYY-MM-DD`。只映射周一至周六；星期日没有课程。系统不查询或推断节假日。

### 10.2 短期事件

短期缺勤或繁忙确认后生成日期例外，不改变基础版本。事件结束后无需回滚，查询后续日期时不会再叠加这些例外。

### 10.3 长期缺勤

持续时间达到设置阈值且只进行了原课节代课时，不需要改变周课表版本，只保存日期范围内的代课例外。

如果长期缺勤方案改变了周课表位置，则：

1. 事件开始所在的未完整周使用日期例外，避免在一周中途切换模板造成课时重复或缺失。
2. 新周课表版本从事件开始后第一个周一生效；如果事件从周一开始，则当天生效。
3. 新版本在调整后的课程位置保留原任课教师；缺勤日期内通过日期例外将其替换为同科代课教师。
4. 缺勤结束后，原教师接手调整后的课程位置。
5. 新版本继续生效，不自动创建恢复旧课表的版本。

新版本生成时必须同时验证代课教师在缺勤期间可用，以及原教师恢复后在新位置长期可用。

## 11. JSON 持久化

正式数据文件为 `backend/data/timetable-data.json`，备份目录为 `backend/data/backups/`。

写入流程：

1. 使用 Pydantic 模型验证完整根对象。
2. 获取进程内写锁并检查请求的 `baseRevision` 与当前 `revision` 一致。
3. 将当前正式文件复制为带时间戳的备份。
4. 将新数据写入同目录临时文件，刷新并同步磁盘。
5. 使用原子替换更新正式文件。
6. 只保留最近 20 份自动备份。

启动时验证 JSON。文件不存在时创建空的合法数据集；文件损坏或模式不合法时，不覆盖原文件，并返回可操作的恢复错误。系统提供列出备份和恢复指定备份的本地接口。

`schemaVersion` 用于以后升级结构。程序拒绝直接加载高于自身支持版本的数据，防止旧程序破坏新格式。

## 12. 后端接口

所有接口均不需要身份令牌。建议统一放在 `/api` 下：

- `GET /api/state`：加载完整应用状态。
- `PUT /api/settings`：保存周课表设置。
- `POST /api/timetables/generate`：生成基础课表候选。
- `POST /api/timetables`：确认保存生成结果。
- `GET /api/timetables`：读取课表版本摘要。
- `GET /api/timetables/{id}`：读取指定版本。
- `POST /api/timetables/{id}/versions`：校验人工编辑并创建不可变的子版本。
- `DELETE /api/timetables/{id}`：删除未被后续版本引用的课表。
- `POST /api/change-proposals`：根据缺勤或繁忙事件生成候选方案。
- `POST /api/changes/apply`：带 `baseRevision` 提交已选方案，后端重新校验后原子保存。
- `GET /api/calendar/day?date=YYYY-MM-DD`：解析指定日期的实际课表。
- `GET /api/changes`：查询已确认变更历史。
- `GET /api/backups`：列出本地备份。
- `POST /api/backups/{name}/restore`：明确确认后恢复备份。

候选方案是无状态响应。应用时客户端回传完整方案及生成时的 `baseRevision`；如果期间数据已变化，后端拒绝应用并要求重新生成。

## 13. 前端流程

### 13.1 启动与导航

根路径直接显示课表管理页。导航保留课表管理、生成课表、编辑课表、智能调课和使用说明。删除 Clerk Provider、登录/注册页、SSO 回调、登录按钮、用户头像和登出逻辑。

原首页中关于 Clerk、云存储和 MongoDB 的文案删除或改为本地存储说明。旧登录相关 URL 重定向到根路径。

人工编辑已生效课表时，“保存”操作创建一个新的子版本，并要求选择生效日期；默认值为当天。系统不会原地覆盖历史版本。

### 13.2 智能调课面板

面板包含：

- 教师选择。
- 事件类型：缺勤或繁忙。
- 缺勤的起止日期，或繁忙的具体日期和课节。
- 事件说明。
- “生成方案”按钮。

结果区并列或分页展示一至三个候选方案。每个方案显示日期/课节差异、原课程和新课程、代课教师、受影响班级/教师/教室/走班块、评分、原因和警告。

用户可以预览指定日期的最终课表，随后点击“确认应用”。放弃或关闭候选方案不修改任何数据。

## 14. 错误处理

- 输入数据不完整：返回字段级错误，不调用求解器。
- 基础规则冲突：返回按班级、教师、课程、教室或走班块分类的诊断。
- Agent 无解：返回无解状态、受影响课程和主要阻塞约束，不返回部分课表供应用。
- 方案过期：`baseRevision` 不一致时返回冲突，要求重新生成。
- 保存失败：保留正式文件和临时文件信息，不报告成功。
- 数据文件损坏：进入只读错误页，允许用户选择有效备份恢复。
- 应用方案：服务端必须再次执行完整校验，不能信任前端提交的候选内容。

## 15. 测试策略

### 15.1 单元测试

- 日期到周一至周六课表的映射。
- 教师资格、不可用课节和冲突校验。
- 缺勤时原课节同科代课优先。
- 缺勤时为了同科代课进行班内调课。
- 繁忙时班内换课优先于代课。
- 各班每周各科课时保持不变。
- 走班块只替换单个分组教师，以及整体移动时的同步约束。
- 长期新版本在教师恢复后持续生效。
- 短期日期例外在结束后不再生效。
- 评分的策略优先级不能被次级成本反转。

### 15.2 持久化测试

- 空数据文件初始化。
- JSON 模式验证。
- 原子保存、版本号递增和旧 revision 冲突。
- 保存失败时正式文件不损坏。
- 自动备份数量限制和恢复。

### 15.3 API 与前端测试

- 基础课表生成、保存、编辑和删除。
- 变更方案生成、放弃和确认应用。
- 应用前二次校验。
- 指定日期实际课表解析。
- 无 Clerk 环境变量时前端正常启动。
- 根路径直接进入课表管理页。
- 前端构建、Lint 和关键交互流程。

## 16. 验收标准

功能完成必须同时满足：

1. 不配置 Clerk 和 MongoDB 即可启动前后端并使用全部核心功能。
2. 基础排课满足课程课时、教师、教室和走班硬约束。
3. 缺勤和繁忙使用真实日期，且遵循各自不同的策略优先级。
4. 所有已应用方案保持班级每周各科课时不变。
5. 走班块不会出现班级、教师或教室不同步。
6. 长期调课版本在原教师恢复后继续生效。
7. Agent 修改前必须展示方案并获得确认。
8. JSON 写入可恢复，异常情况下不会静默损坏正式数据。
9. 自动测试通过，前端生产构建成功，后端可在本机启动并完成核心接口验证。
