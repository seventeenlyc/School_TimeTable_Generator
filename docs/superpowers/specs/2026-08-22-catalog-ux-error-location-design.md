# 基础数据录入体验与错误定位设计

日期：2026-08-22

## 1. 目标

本次修改不引入教师固定带班模型，也不限制教师负责班级的数量。重点改善基础数据录入、耗时操作反馈和错误诊断，并修复修改课程要求教师后已有课表资源索引失效的问题。

目标包括：

1. 取消测试样例及说明中“普通教师最多负责两个班级”的系统性表述；正式系统允许同一教师承担任意数量班级的课程要求。
2. 新增教师和课程要求时，将新记录显示在列表首位，并通过进入动画和自动聚焦强化反馈。
3. 保存、生成、计算、应用、恢复和删除等异步操作统一显示按钮级加载效果，并阻止重复提交。
4. 将后端结构化错误转换为可读的中文错误项，显示原因和数据位置，彻底避免 `[object Object]`。
5. 错误项可点击，自动切换标签、滚动、聚焦并高亮对应记录或字段。
6. 修改课程要求教师时，自动重建所有已有课表的教师和教室资源索引；若重建后的课表合法则允许保存，否则返回精确冲突位置。

## 2. 非目标

- 不新增 `assigned_class_ids` 等教师固定带班字段。
- 不根据教师负责班级数量阻止保存或排课。
- 不改变缺勤、繁忙、代课和换课的既定优先级。
- 不重写基础排课求解算法。
- 不自动重排已有教师和课程要求；只把本次新增的记录放到首位。

## 3. 基础数据新增行为

### 3.1 新增教师

点击“添加教师”后，新教师对象插入 `teachers` 数组首位。页面自动滚动到新教师卡片，播放约 400 毫秒的淡入、轻微位移回弹及边框高亮动画，随后聚焦教师姓名输入框。

### 3.2 新增课程要求

点击“添加课程要求”后，新课程要求插入 `course_requirements` 数组首位。页面自动滚动到该记录，播放同样的进入动画，随后聚焦班级选择框。

### 3.3 顺序保持

基础数据保存后，后端按照请求数组顺序持久化数据。重新加载时保持该顺序，不进行按 ID、名称或创建时间的隐式排序。

## 4. 异步按钮加载反馈

提供可复用的加载按钮表现：

- 请求开始后立即禁用按钮，避免重复提交。
- 原图标切换为旋转加载图标。
- 文案按操作切换为“保存中…”“生成中…”“计算中…”“应用中…”“恢复中…”或“删除中…”。
- 按钮保持稳定宽度，避免布局跳动。
- 请求成功或失败后恢复原状态。

覆盖以下操作：

- 保存基础数据和系统设置；
- 生成课表预览和确认保存课表；
- 保存手动调整后的课表；
- 生成调课方案和应用调课方案；
- 恢复本地备份；
- 删除课表等需要后端确认的异步操作。

页面首次获取数据继续使用页面级加载状态，不纳入按钮组件。

## 5. 结构化错误模型

前端将各种后端错误统一归一化为错误项。每个错误项至少包含：

- `code`：稳定错误代码；
- `title`：面向用户的错误类型；
- `message`：可读原因；
- `location`：面向用户的数据位置描述；
- `target`：可选的定位信息，包括标签、实体类型、实体 ID、字段、课表版本、星期和节次；
- `related_targets`：重复数据或冲突涉及的其他位置。

API 客户端必须支持以下响应形态：

- 纯字符串 `detail`；
- 带 `message` 的对象；
- 校验报告中的 `errors`、`warnings`；
- 日历或调课冲突中的 `issues`；
- 排课失败的 `diagnostics`；
- 无法识别的结构化对象。

无法识别的对象不得隐式转为字符串，而应生成包含错误代码和安全摘要的兜底错误项。

## 6. 错误弹窗与点击定位

错误以可展开弹窗或错误面板展示。每条错误显示错误类型、原因和位置。

点击错误项后：

1. 关闭弹窗或收起遮挡内容；
2. 切换到对应基础数据标签；
3. 根据稳定实体 ID 找到目标记录；
4. 将记录滚动到可视区域；
5. 播放红色边框闪烁动画；
6. 聚焦对应字段。

同一错误关联多条记录时，界面提供“查看下一处”，在所有相关目标间循环定位。

课表冲突的位置至少包含课表名称、星期、节次、教师和相关班级。若目标位于课表页面，则跳转或定位到对应课表视图；若目标属于基础数据，则定位到对应基础数据记录。

## 7. 课程要求唯一性

普通课程要求以 `(class_id, subject_id)` 为唯一组合。

- 同一班级、同一科目、不同教师：返回“同一班级同一科目配置了两个不同教师”，并关联两条课程要求。
- 同一班级、同一科目、相同教师：返回“课程要求重复录入”，并关联两条课程要求。

走班块按自身同步分组规则校验，不与普通课程要求进行错误的重复判定。

前端在保存前提供相同的快速校验，后端仍作为最终权威校验层，防止绕过前端的无效请求被持久化。

## 8. 修改教师后的已有课表同步

课程格引用课程要求 ID，因此课程要求中的教师改变会影响所有引用该要求的已有课表。保存基础数据时必须执行以下事务流程：

1. 用新基础数据替换候选状态中的基础目录字段。
2. 重新生成教师的 `teaching_assignment_ids` 关联。
3. 对候选状态中的每个课表版本调用资源索引重建，更新教师和教室课表索引。
4. 使用新基础数据完整校验每个课表版本。
5. 校验历史变更引用。
6. 全部通过后由 JSON 仓库执行备份和原子写入。

任何课表产生真实教师撞课、教师不可用、教室冲突、课时错误或无效引用时，整个保存操作失败，不写入部分数据。返回的结构化错误必须包含版本 ID、星期、节次和相关实体 ID，以供前端翻译并定位。

已确认案例：高一(3)班语文从“语文老师02”修改为“语文老师01”后，基础目录合法；重建已有课表资源索引后课表也合法，因此保存应成功。

## 9. 测试策略

后端测试覆盖：

- 同一教师可承担超过两个班级的课程要求；
- 相同班级和科目的同教师重复及不同教师重复；
- 修改课程教师后自动重建所有课表资源索引；
- 重建后合法时保存成功；
- 重建后产生冲突时保存失败且不改变 JSON；
- 冲突报告包含版本、星期、节次和相关实体。

前端测试覆盖：

- 新教师和新课程要求插入首位；
- 新记录自动滚动、聚焦和高亮；
- 各异步按钮在等待期间禁用、显示旋转图标和动作文字；
- 字符串及结构化 API 错误的统一解析；
- 页面永不显示 `[object Object]`；
- 点击错误切换标签并定位对应记录；
- 重复课程要求错误能够在两处之间循环定位。

最后运行后端全量测试、前端单元测试、前端 lint 和生产构建，并在本地页面复现高一(3)班语文教师修改流程。
